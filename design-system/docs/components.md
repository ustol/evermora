# Components

## Buttons

- `default`: one primary action per section. Use for “Create a memorial”, “Leave a tribute”, or “Save changes”.
- `outline`: secondary navigation or safe alternatives.
- `ghost`: low-emphasis actions inside dense card or list contexts.
- `destructive`: moderation, deletion, and report resolution only.

Use sentence case. Avoid celebratory labels for grief-adjacent tasks.

## Cards

Cards frame memorial summaries, contribution previews, funeral detail panels, and admin lists. They should include:

- a clear heading or memorial name,
- supportive metadata (dates, hometown, relationship),
- at most one primary action,
- enough padding for touch and emotional clarity.

## Forms

Contribution forms should reduce cognitive load:

- persistent labels above inputs,
- helper text for why information is requested,
- visible validation tied to `--semantic-critical`,
- grouped sections for personal details, funeral arrangements, story, photos, and privacy.

## Memorial contribution patterns

- Tribute cards should foreground the message and contributor relationship.
- Gift/wreath actions are supportive, not transactional; use warm gold sparingly.
- Empty states should invite gentle next steps: “Be the first to leave a tribute” rather than “No data”.
- Public memorial pages should favor reading rhythm over dashboard density.
